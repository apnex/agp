# AGP MVP — endpoint routing, RIB, and forwarding design

| Field | Value |
|---|---|
| Status | Proposed |
| Date | 2026-07-29 |
| Runtime scope | One hub router and directly connected spokes |
| Planning input | [AGP MVP survey](../../../surveys/agent-gateway-protocol-mvp-survey.md) |
| Related contracts | [`protocol.md`](protocol.md), [`sdk-operations.md`](sdk-operations.md) |

## 1. Decision and scope

The hub owns the authoritative endpoint routing state. It receives named
endpoint advertisements from established spoke sessions, retains every
candidate, selects exactly one route per endpoint, and resolves that route
through an abstract next hop before forwarding a JSON data envelope.

The MVP implements:

- router-local endpoints and directly learned spoke endpoints;
- authoritative session-scoped endpoint sets, with omission as withdrawal;
- an Adj-RIB-In-equivalent candidate view, a selected RIB, and a forwarding
  view;
- deterministic duplicate selection;
- atomic cleanup and reselection on session loss; and
- immutable, revisioned operational snapshots.

The MVP does **not** implement router peering, route export/Adj-RIB-Out,
inter-router propagation, path-vector selection, loop prevention, policy, or
multipath forwarding. Optional path attributes exist only as an in-memory
extension seam and have no MVP wire or selection semantics.

This follows survey Q1 `a,c` (correct and visible routing), Q2 `a,c`
(developer and operator surfaces), Q3 `b,c` (contract-first layered design),
Q4 `a,b` (generic next hop and extensible RIB), and Q5 `a,b` (continuous
hub-and-two-spoke proof). In particular: **defer multi-hop behaviour, preserve
the model**.

## 2. BGP terminology and AGP adaptation

[RFC 4271 §3.2](https://www.rfc-editor.org/rfc/rfc4271.html#section-3.2)
separates inbound routing information (`Adj-RIBs-In`), locally selected routes
(`Loc-RIB`), and routes prepared for export (`Adj-RIBs-Out`). It also says that
these are conceptual views rather than a requirement for three physical
copies. AGP uses the same useful separation:

| AGP view | BGP analogy | MVP meaning |
|---|---|---|
| Advertisement ledger | Received UPDATE state | Endpoint claims owned by one established session |
| Candidate RIB | Adj-RIBs-In plus local inputs | All feasible and infeasible local and learned/direct candidates |
| Selected RIB | Loc-RIB | One winning route for each reachable endpoint |
| Forwarding view | Routing/FIB view | Selected route resolved to a usable local or session next hop |

The analogy is deliberately not equivalence. AGP routes exact endpoint names,
not IP NLRI. The candidate RIB also includes router-local originations.
Adj-RIB-Out is absent because inter-router export is deferred.

RFC 4271 also treats closing a peer connection as implicit withdrawal of all
routes learned from it. AGP adopts that lifecycle rule, strengthened into one
observable atomic state transaction.

The useful seed in [`socket/api.js`](../../../socket/api.js) is its
per-connection route ownership and whole-set replacement. AGP preserves that
ownership but replaces socket-derived keys, mutable global maps, and direct
connection coupling with stable identities, explicit transactions, selection,
and next-hop resolution.

## 3. Identities and ownership

### 3.1 Canonical identities

| Entity | Identity | Lifetime and authority |
|---|---|---|
| Node | `nodeId` | Stable, opaque, configured protocol identity; retained across reconnects |
| Peer | no separate ID | Relationship to the remote `nodeId` on a session |
| Local session | `owningSessionId` | Hub-local ID for one FSM attempt; route cleanup and stale callbacks key on it |
| Origin session | `originSessionId` | Remote `sessionId` received in OPEN; meaningful with `originNodeId`, and scopes that sender's messages and endpoint-update revisions |
| Transport | private `transportId` | One concrete WebSocket; adapter-internal and never present in route/query DTOs |
| Endpoint | `endpoint` | Canonical protocol name and exact routing key |
| Route | `routeId` | Router-local opaque ID for one candidate's lifetime |

`nodeId` is the sole stable participant identity. Socket address tuples are
optional diagnostics only. `owningSessionId` and `originSessionId` are both
reconnect-scoped but are not interchangeable: the first identifies the local
FSM object; the second is asserted by the remote node in OPEN. A stale callback
can affect state only when its local `owningSessionId` still owns that state.

The reference default session ID is exactly six lowercase hexadecimal
characters generated by a node-local, nonrepeating 24-bit cursor from a random
starting point. It is intentionally not globally unique. The hub requires
`owningSessionId` to be unique within its own live session registry, whereas
origin provenance is the composite `(originNodeId, originSessionId)`. Thus two
different spokes may legitimately advertise the same `originSessionId`
without aliasing one another.

Every hub has an explicit identity-admission policy that accepts or rejects the
OPEN `nodeId` before establishment. Development mode may explicitly configure
and expose a `self-asserted` policy; it is never an implicit absence of policy.
The hub rejects a second session attempt for a remote `nodeId` while any
identity-bound controller for that node remains nonterminal. This includes
`OpenConfirm`, `Established`, and closing cleanup; the registry entry is
released only after terminal teardown. That attempt receives
`IDENTITY_COLLISION`, which is fatal to the colliding transport but retryable
with bounded backoff by a legitimate spoke. A credential-to-identity failure
instead receives permanent `IDENTITY_REJECTED`.

Endpoint names use the protocol contract:

```text
^[a-z0-9][a-z0-9._-]{0,62}(?:/[a-z0-9][a-z0-9._-]{0,62})*$
```

They are lowercase ASCII, at most 253 characters, and compared byte-for-byte.
No wildcard, prefix, locale, or case-folded matching exists in the MVP.

### 3.2 Route source classes

`routeClass` has two values in the MVP:

- `local`: originated by an active endpoint binding in the hub's own SDK;
  `originNodeId` is the hub `nodeId`, with no source session.
- `learned`: received from a session. Its MVP `learnedKind` is always
  `direct`; `originNodeId` is the advertising spoke `nodeId`,
  `originSessionId` is the remote OPEN session, and `owningSessionId` is the
  hub-local FSM session that owns cleanup.

The independent `sourceKind` dimension is `local | session`; it answers who
owns the candidate, while `routeClass` answers whether reachability was locally
originated or learned. This distinction is present now so future learned
multi-hop candidates do not require a replacement DTO.

A spoke owns its local registration and endpoint-export state, but it does not
own or mirror the hub's received-advertisement ledger or selected RIB/FIB. A
spoke send is admitted to its established hub session; it cannot claim which
route the hub later selects.

### 3.3 Advertisement ownership

An advertisement key is:

```text
(originNodeId, originSessionId, endpoint)
```

Only an `Established` spoke session can submit its own authoritative set. A hub
record additionally stores `owningSessionId`, and a session cannot mutate
another local owner's advertisements. Repeating the same full set at the next
revision is idempotent at the route-state level.
The hub's cleanup index is `(owningSessionId, endpoint)`, so teardown never
depends on a remote-supplied ID. Hub-local registrations create local
candidates directly; they are queryable local endpoints but are not entries in
the received-advertisement ledger.

Each `endpoint.update` carries the sender's complete desired `endpoints[]` set,
not a delta. The hub atomically replaces the set owned by that session:
new names are announcements, retained names remain, and omitted names are
withdrawals. The update still obeys the remote origin session's revision
sequence: first revision `1`, then exactly the previous consumed revision plus
one. A syntactically and sequentially valid update rejected by authorization or
policy consumes that revision but makes no advertisement, candidate, selection,
or forwarding mutation; see §6.1.

The session nevertheless retains two bounded intent sets, each capped by the
negotiated endpoint limit: `lastClaimedEndpoints` from the most recently
consumed authoritative update and `rejectedEndpoints` with the stable rejection
reason for that update. They are protocol/session evidence, not advertisements
or routes, and disappear on teardown. They let the data plane distinguish a
claimed-but-not-active source after a rejection from one never claimed.

The mandatory identity-admission policy binds the remote `nodeId`. A separate
endpoint-admission policy authorizes which canonical names that admitted node
may claim. Development mode may explicitly configure endpoint `allow-all`; an
`admission-port` mode requires the SDK port and can bind namespaces to the
identity-admitted node. Both sanitized modes are visible in configuration and
session/endpoint operations without changing route keys. Ordinary updates
authorize only newly added names in the context of the complete desired and
currently accepted sets. When there are no additions, the update is
auto-allowed without invoking external endpoint policy, so a pure withdrawal
cannot fail on callback behavior. Retained names remain authorized for that
session;
ordinary updates cannot revoke one retained name. The MVP has no per-session
administrative-stop API, so a changed policy for an accepted name takes effect
on natural session replacement or host-wide router stop/restart, which
withdraws all routes from that session; it is not a partial update side effect.

## 4. Canonical route model

The logical records below may share storage, but their boundaries and query
meaning are normative.

```ts
type NextHopRef =
  | { kind: "local"; bindingId: string }
  | { kind: "session"; nodeId: string; owningSessionId: string };

type SelectedReason =
  | "ONLY_ELIGIBLE"
  | "PREFER_LOCAL"
  | "LOWEST_ORIGIN_NODE_ID"
  | "LOWEST_ORIGIN_SESSION_ID";

type CandidateSelectionReason =
  | SelectedReason
  | "DUPLICATE_NOT_SELECTED"
  | "LOCAL_BINDING_INACTIVE"
  | "ADVERTISEMENT_INACTIVE"
  | "SESSION_NOT_ESTABLISHED"
  | "NEXT_HOP_UNRESOLVED";

interface SessionEndpointIntent {
  owningSessionId: string;
  originNodeId: string;
  originSessionId: string;
  consumedRevision: string;
  lastClaimedEndpoints: readonly string[];
  rejectedEndpoints: Readonly<Record<
    string,
    "POLICY_REJECTED" | "CAPACITY_REJECTED"
  >>;
}

interface AdvertisementSnapshot {
  advertisementId: string;
  endpoint: string;
  sourceKind: "session";
  originNodeId: string;
  originSessionId: string;
  owningSessionId: string;
  updateRevision: string;
  receivedAt: string;
}

interface CandidateRouteSnapshot {
  routeId: string;
  endpoint: string;
  sourceKind: "local" | "session";
  routeClass: "local" | "learned";
  learnedKind?: "direct";
  originNodeId: string;
  originSessionId?: string;
  owningSessionId?: string;
  advertisementId?: string;
  nextHop: NextHopRef;
  eligible: boolean;
  selectionStatus: "selected" | "not-selected" | "ineligible";
  selectionReason: CandidateSelectionReason;
  attributes?: Readonly<Record<string, JsonValue>>;
  installedAt: string;
}

interface SelectedRouteSnapshot {
  endpoint: string;
  routeId: string;
  routeClass: "local" | "learned";
  learnedKind?: "direct";
  originNodeId: string;
  nextHop: NextHopRef;
  selectedAt: string;
  selectionReason: SelectedReason;
}

interface ForwardingEntrySnapshot {
  endpoint: string;
  selectedRouteId: string;
  nextHop: NextHopRef;
  resolvedSessionId?: string;
}
```

`attributes` is absent for every MVP directly learned route and ignored by the MVP
decision process. Unknown or speculative attributes must not be accepted from
the MVP wire. Its presence in the internal/query type only prevents later
learned-route metadata from requiring a replacement route model.
For a session advertisement, `updateRevision` is the latest accepted
authoritative revision that confirmed the endpoint.

The `NextHopRef` is not a WebSocket:

- `local` resolves through the endpoint-binding registry;
- `session` resolves through the session directory, which verifies matching
  `nodeId`, matching local `owningSessionId`, and state `Established`, then
  obtains the private writable transport handle. The resulting local session ID
  appears as `resolvedSessionId`; the private `transportId` never does.

The forwarding entry is derived state, not an independent source of truth. It
exists only for a selected route whose next hop resolved in the same
transaction; no observable snapshot contains an unusable forwarding entry.

## 5. Eligibility and deterministic selection

### 5.1 Eligibility

A local candidate is eligible only while its exact binding is active. A
`learned/direct` candidate is eligible only while:

1. its advertisement exists;
2. advertisement and route have the same endpoint, origin node, origin
   session, and local owning session;
3. the owning session is bound to that origin node/session and is
   `Established`; and
4. the next-hop resolver resolves that same local owning session.

Queue saturation is a per-message forwarding failure, not route ineligibility.
A transport close changes the FSM/session state before routing is recomputed.

### 5.2 Duplicate endpoint policy

Different sessions may advertise the same endpoint. This is not a wire error.
Each claim remains an independently visible candidate, but the MVP installs
exactly one selected route; there is no load balancing.

Eligible candidates are sorted by this public, total ordering:

1. `local` before `learned`;
2. lower `originNodeId`, compared as unsigned UTF-8 bytes;
3. lower `originSessionId`, compared as unsigned UTF-8 bytes (`local` has no
   tie at this step).

There can be only one local binding and one candidate per
`(originNodeId, originSessionId, endpoint)`. A second live session for one node
is rejected during identity admission, so the tuple is total. Event
arrival time and random `routeId` never influence selection.

Selected-route reasons are observable:

- `ONLY_ELIGIBLE`;
- `PREFER_LOCAL`;
- `LOWEST_ORIGIN_NODE_ID`;
- `LOWEST_ORIGIN_SESSION_ID`.

Unselected eligible candidates report `DUPLICATE_NOT_SELECTED`; ineligible
candidates report exactly one of `LOCAL_BINDING_INACTIVE`,
`ADVERTISEMENT_INACTIVE`, `SESSION_NOT_ESTABLISHED`, or
`NEXT_HOP_UNRESOLVED`. Withdrawal of the winner promotes the next eligible
candidate in the same transaction. When no eligible candidate exists there is
no selected-route row: `NO_ELIGIBLE_ROUTE` is carried by the
`route.changed/unreachable` event and counter, while each retained candidate
still exposes its own feasibility reason.

```text
select(endpoint):
  candidates := candidateRib[endpoint]
  for candidate in candidates:
    candidate.eligible := resolveEligibility(candidate)
  eligible := candidates where eligible
  winner := first(sort(eligible, routeClass, originNodeId, originSessionId))
  selectedRib[endpoint] := winner, or delete when none
  forwarding[endpoint] := resolve(winner.nextHop), or delete when none
```

## 6. State transactions

All session and route mutations run on one serialized canonical SDK state
executor. Each commits one monotonically increasing operations `revision`;
snapshots never expose a partially applied transaction. Session-loss FSM,
advertisement, selection, and forwarding events therefore share one revision.
Protocol endpoint-update revisions and the operations revision are different
counters.

Potentially asynchronous identity/endpoint admission callbacks never run while
holding that executor. They operate on immutable input under a finite deadline,
then re-enter with a session/request token and revalidate all preconditions
before one commit. Stale completions are discarded. Only the requesting
session's bounded inbound sequence waits for its result; other sessions, timers,
queries, and route transactions continue.

If that session cannot reserve both the next continuation entry and its exact
encoded bytes, the core invalidates the request token, records
`INBOUND_ADMISSION_OVERFLOW`, and force-aborts the transport without attempting
an ordered notification. The late callback cannot consume an endpoint-update
revision or mutate route state. If the callback belonged to an established
session, the resulting ordinary session teardown still withdraws all routes
owned by that session.

### 6.1 Bounded admission

The reference defaults are deliberately finite:

| Limit | Default | Version-1 constraint |
|---|---:|---:|
| Active sessions | 64 | Configurable positive integer |
| Router-local endpoints | 256 | Configurable positive integer |
| Active endpoints per spoke session | 64 | Configurable; hard maximum 256 |
| Total candidate routes, including local | 4,352 | Configurable; must satisfy the invariant below |
| Retained transitions per current session | 64 | Bounded ring, maximum 64 |

Implementations may reject configuration they cannot safely support. Live
advertisement/candidate/selected/forwarding query lists are never truncated:
the state itself is bounded. Current-session transition rings and subscriber
buffers are separately bounded and expose dropped counters.

Configuration validation enforces:

```text
maxCandidateRoutes >=
  maxLocalEndpoints
  + (maxConcurrentSessions * maxEndpointsPerSession)
```

The defaults satisfy this exactly. Session and local-endpoint admission enforce
their own configured maxima, so a syntactically valid set from an already
admitted session cannot later fail because the global candidate store is full.

Before applying an expected `endpoint.update`, the hub validates the complete
authoritative set. If endpoint authorization/policy rejects any added names or
the set exceeds the negotiated per-session limit, it rejects the entire update
with correlated `ENDPOINT_REJECTED` listing the denied additions. No
route entity changes and no subset is installed. The transaction advances the
session's consumed update revision, retains the claimed/rejected intent sets,
increments the operations revision, and records the rejection. The spoke must
send its next full set at the next
revision, excluding rejected names; it must not replay the rejected revision.
For a capacity rejection, the list is every newly added name in canonical
order; this deterministic fail-closed result leaves the prior accepted set
active and guarantees the successor excluding those additions fits.

There is no route/failure event history and no event replay in the MVP.
Canonical operations retain current state, counters, the current session's
at-most-64-transition ring, and bounded subscriber buffers. A subscriber gap
requires a fresh current snapshot.

### 6.2 Endpoint update

```text
applyEndpointUpdate(session, message):
  require session.role == spoke
  require session.state == Established
  require message.revision == session.endpointRevision + 1
  desired := validate canonical, unique endpoints array
  current := immutable snapshot of endpoint set owned by session
  additions := desired - current
  if additions is empty:
    result := allow without invoking endpoint policy
  else if desired.size > negotiated maxEndpointsPerSession:
    result := reject CAPACITY with every addition in canonical order
  else:
    authorize additions outside canonical executor in context of desired/current
    re-enter with request token; require same live session, revision, and current
    result := the validated authorization result

  if result rejects:
    transaction:
      session.endpointRevision := message.revision
      session.lastClaimedEndpoints := desired
      session.rejectedEndpoints := offending added endpoints with stable reasons
      record ENDPOINT_REJECTED(offending added endpoints) without route mutation
      increment operations revision once
    return correlated rejection

  transaction:
    removed := current - desired
    added := desired - current
    retained := current intersect desired
    affected := removed union added
    for endpoint in removed:
      delete session-owned advertisement and candidate
    for endpoint in added:
      create session-owned advertisement and learned/direct candidate
    for endpoint in retained:
      update advertisement's last-confirmed revision only
    session.endpointRevision := message.revision
    session.lastClaimedEndpoints := desired
    clear session.rejectedEndpoints
    recompute selected RIB and forwarding for every affected endpoint
    increment operations revision once
  publish committed events
  send endpoint.ack only after the accepted transaction commits
```

Invalid, duplicate, or skipped update revisions follow `protocol.md`; none may
partially mutate the RIB. Syntax, shape, and revision-sequence failures do not
consume a revision. Expected updates rejected by policy consume it as specified
above. Because every later update is authoritative, the next accepted revision
reconciles the hub even after a consumed rejection.

### 6.3 Local registration

Registering a hub-local endpoint creates one local candidate and recomputes
that endpoint. Duplicate local registration is rejected by the endpoint
registry. Unregistration atomically removes its candidate and promotes any
eligible learned/direct candidate.

### 6.4 Session loss

```text
removeSession(ownerId, reason):
  transaction:
    mark session non-Established before next-hop resolution
    owned := all advertisements/candidates with
             owningSessionId == ownerId
    affected := distinct endpoints in owned
    delete owned advertisements and candidates
    delete bounded last-claimed/rejected endpoint intent for ownerId
    recompute every affected endpoint
    increment operations revision once
  publish withdrawal, selection, forwarding, and session events
```

This applies to clean close, timeout, protocol failure, and stop. Cleanup is
idempotent. Late frames/callbacks carrying the old local `owningSessionId`
cannot recreate state, even if they repeat a remote identity. Observers see
either all old routes or the complete post-loss state, never an intermediate
table.

## 7. Data-plane source validation and forwarding

Source ownership is checked before destination forwarding:

1. For a router-local send, the source endpoint must have an active local
   candidate and that candidate must be the selected source route.
2. For an inbound spoke envelope with no active candidate, the session's
   bounded last-claimed/rejected intent is checked.
3. Otherwise, a candidate for the exact `(source endpoint, origin node, origin
   session, local owning session)` must exist.
4. That candidate must also be the hub's selected route for the source
   endpoint.

If the latest consumed update carries retained rejection context and a missing
active source occurs in its `lastClaimedEndpoints`, the raced or known-rejected
message is dropped with recoverable `SOURCE_NOT_ACTIVE` and its stable
`POLICY_REJECTED`, `CAPACITY_REJECTED`, or
`UPDATE_NOT_INSTALLED` reason; the last applies to an otherwise allowed name in
a whole set rejected because of another name. The session remains established.
If it was never claimed, `SOURCE_NOT_OWNED` is a fatal protocol
violation and the session closes. If step 4 fails, the source is advertised but is a
losing duplicate: `SOURCE_NOT_SELECTED` is a nonfatal policy/delivery error,
the envelope is dropped, the session remains established, and the event and
counter are observable. This prevents replies to a named source from being
routed to a different owner.

```text
forward(envelope, ingress):
  validateSelectedSource(envelope.source, ingress)
  route := selectedRib[envelope.destination]
  if absent: emit NO_ROUTE; return delivery error
  egress := nextHopResolver.resolve(route.nextHop)
  if absent: recompute(destination); emit DESTINATION_UNAVAILABLE; return error
  if egress.kind == local:
    atomically reserve one handler-execution slot plus active payload bytes
    if either handler bound is full: emit BACKPRESSURE; return error
    return admitted
  if envelope.utf8Bytes > egress.session.peerReceiveLimitBytes:
    emit DESTINATION_LIMIT_EXCEEDED; return error
  atomically reserve one message slot plus encoded bytes in session/global queue budgets
  if either bound is full: emit BACKPRESSURE; return error
  return admitted
```

The route plus local binding or peer session is revalidated at admission,
so binding/session loss cannot admit onto a stale target. A local next hop has
no peer receive limit; it is already within the receiving router's envelope
limit and must immediately reserve one bounded handler-execution slot plus its
active payload bytes; the MVP has no handler waiting backlog. Handler completion
releases both reservations. Failure after admission is a local event/counter
and cannot retroactively alter the receipt or produce a data success/failure
ACK. AGP makes one ordered forwarding attempt.
It does not replay, acknowledge application handling, or promise remote
delivery. This matches
[ADR-0006](decisions/0006-local-admission-delivery-semantics.md).

## 8. Query DTOs and events

The hub SDK exposes one detached, deeply immutable snapshot:

```ts
interface RoutingSnapshot {
  revision: string;       // non-negative decimal integer
  capturedAt: string;     // RFC 3339 UTC time of this revision's commit
  advertisements: readonly AdvertisementSnapshot[];
  candidateRoutes: readonly CandidateRouteSnapshot[];
  selectedRoutes: readonly SelectedRouteSnapshot[];
  forwarding: readonly ForwardingEntrySnapshot[];
}
```

Snapshot rows are exactly the canonical DTOs from §4. Arrays are sorted by
endpoint, then origin node, then origin/local-owner session so JSON and CLI
output are deterministic. `transportId`, WebSocket objects, credentials,
callbacks, and mutable maps are never exposed.

MVP list queries return complete bounded lists and define no filtering
parameters. The read-only HTTP adapter serializes these same DTOs; it does not
reconstruct routing state. `advertisements()`, `routes()`, and `forwarding()`
are hub routing queries and return complete empty shapes on a spoke; the
aggregate routing arrays are empty there too. A spoke exposes its pending,
acknowledged, and rejected outbound endpoint state through local endpoint and
session snapshots, with no claim to the hub's selected RIB/FIB.

Routing publishes through the SDK's closed event/data union:

| SDK `kind` | Exact `data.change` values or code field |
|---|---|
| `advertisement.changed` | `added`, `updated`, `removed` |
| `route.changed` | `candidate-added`, `candidate-updated`, `candidate-removed`, `selected`, `reselected`, `unreachable` |
| `forwarding.changed` | `installed`, `replaced`, `removed` |
| `protocol.notification` | `data.code = SOURCE_NOT_OWNED` |
| `protocol.error` | `data.code` is one closed recoverable protocol-error code |
| `message.failed` | `data.code` is the closed local/forwarding failure outcome |
| `queue.pressure` | `data.reasonCode = BACKPRESSURE` |

Every event includes the canonical operations revision, timestamp, endpoint
where applicable, action/reason code, and relevant node/session/route IDs. All
session and route events from one state transaction share its revision and are
published only after commit. Counters for each failure reason are included in
operations snapshots.

## 9. Failure rules and invariants

Normative invariants:

1. No endpoint, advertisement, candidate, selected route, or forwarding entry
   contains or keys on a WebSocket/socket address.
2. No learned/direct candidate exists without exactly one owning
   advertisement, origin session, and local owning session.
3. Only `Established` local owning sessions contribute eligible learned/direct
   candidates.
4. At most one route and forwarding entry is selected per endpoint.
5. A forwarding entry always references the same `routeId` and `nextHop` as
   the selected RIB entry at that revision.
6. Session loss removes every owned route before the cleanup revision is
   observable.
7. Selection is independent of update arrival and map iteration order.
8. Data from a spoke is accepted only when that exact origin/local-session pair
   owns the selected source route.
9. Unknown destination and unavailable next hop are nonfatal data-delivery
   errors; unowned source is fatal.
10. A route update either commits route changes in full or makes no route
    mutation; authorization/policy/admission rejection may advance only protocol and
    operational revision state as explicitly defined in §6.1.

Malformed endpoint updates, wrong-role updates, and updates received outside
`Established` are protocol failures defined by `protocol.md`. Resource limits
reject the whole update rather than install a prefix of it.

## 10. Multi-hop seams

Future router peering can add learned kinds beyond `direct`, path attributes,
policy, Adj-RIB-Out, and path-vector loop prevention while retaining:

- endpoint as the destination key;
- origin node, origin-session, and local-owner-session provenance;
- candidate-to-selected decision boundary;
- `NextHopRef.session` as the immediate neighbor rather than final origin;
- next-hop resolver and forwarding admission boundary; and
- revisioned queries/events.

No MVP component may synthesize path attributes, advertise hub-selected routes
to other routers, or imply that the lexicographic direct-route tie-break is a
future inter-router best-path algorithm.

## 11. Acceptance and conformance criteria

The routing design is satisfied when automated tests prove:

1. Hub-local and directly advertised endpoints create the expected candidate,
   selected, and forwarding rows with no socket handles.
2. `endpoint.update` is Established-only, sequential, authoritative,
   atomic, and idempotent at route-state level. A policy/admission rejection
   consumes the expected revision, lists offending newly added endpoints in
   `ENDPOINT_REJECTED`, and leaves every route view unchanged; the next
   accepted full set resynchronizes state.
3. Two spokes advertising the same endpoint produce two candidates and the
   same winner regardless of arrival order.
4. A local route wins over a duplicate learned/direct route; removing it
   atomically promotes the deterministic learned/direct winner.
5. Omission from the next authoritative set and every session-loss path remove
   all and only the affected routes owned by that session, then promote
   alternatives.
6. A stale callback from a prior reconnect cannot mutate the new session's
   routes.
7. A selected source forwards; a never-claimed source closes with
   `SOURCE_NOT_OWNED`; a claimed-but-inactive source gets
   `SOURCE_NOT_ACTIVE`; and an advertised losing source gets
   `SOURCE_NOT_SELECTED`.
8. Unknown destination, vanished next hop, destination receive-limit excess,
   and full egress queue return the specified error/event without corrupting
   the RIB.
9. SDK snapshot, HTTP JSON, and CLI projection agree on route IDs, selection
   reasons, and revision during the hub-and-two-spoke integration topology.
10. Disconnecting the selected spoke and sending after the cleanup revision
    either uses the promoted route or reports unreachable; it never uses the
    old transport.

## 12. Open and deferred decisions

No MVP routing semantic in this document is left open: a second live session
for one `nodeId` is rejected, hub-local endpoints are supported, limits have
reference defaults, and the duplicate-route order is fixed.

The concrete production credential mechanism used by the mandatory
identity-admission policy is a deployment/security decision; the MVP includes
an explicit observable development `self-asserted` mode. Inter-router
identity, learned-route attributes, export policy, best-path selection, and
loop prevention are deliberately deferred to the multi-hop design rather than
being unresolved MVP behaviour.
